# ICD-10-CM FY27: decisions pending

## Model the Tabular List instructional content

The FY27 CDC/NCHS `icd10cm-tabular_-2027.xml` contains coding instruction elements at more than one level of the classification: chapters, structural groups (`section`), and individual diagnosis entries (`diag`). The currently observed legacy OCL extras cover `EXCLUDES1`, `EXCLUDES2`, `USE ADDITIONAL`, `CODE FIRST`, `CODE ALSO`, and `Note`, but the current FY27 XML additionally carries `includes`, `inclusionTerm`, `sevenChrNote`, and `sevenChrDef`. This needs an explicit modeling decision because these are not incidental display text: they qualify how a code may be assigned, and a refresh that preserves only the currently stored legacy extras will omit instruction content on newly added codes and will not correct changed instructions. The decision is whether each instruction family is represented as a distinct structured property, as a typed OCL description, or by a documented mixed model; whichever representation is chosen must be regenerated from the XML for every FY27 concept rather than copied selectively from the FY25 export.

`Excludes1` and `Excludes2` must remain separate even if both are presented as explanatory concept text. `Excludes1` is a “not coded here” instruction: the excluded condition is mutually exclusive with the code or category and should not be assigned together. `Excludes2` is a “not included here” instruction: the excluded condition is not part of the represented condition, but both conditions may be present in the same patient and may therefore be coded together. Collapsing them into a single `Excludes` field loses a material coding distinction. In the FY27 XML, `excludes1` occurs 2,581 times on `diag`, 65 times on `section`, and twice on `chapter`; `excludes2` occurs 1,092 times on `diag`, 63 times on `section`, and 17 times on `chapter`. They are therefore not limited to groups or chapters.

## Confirm the XML-structural concept-class projection

The selected projection uses the XML's own structural vocabulary rather than invented labels: `Root` for the synthetic `ICD-10-CM` root, `Chapter` for `<chapter>` ranges such as `A00-B99` and `V00-Y99`, `Section` for `<section>` ranges such as `A00-A09` and `V00-V99`, and `Diagnosis` for `<diag>` entries plus concrete seventh-character extensions from the order file. The XML validates the structural role through these element names even though it does not itself carry an OCL `concept_class` field. This replaces the legacy staging simplification that calls every node `Diagnosis`; final confirmation is still needed before the update changes the class of existing structural concepts.

## Review the provisional editorial-section hierarchy rule

The FY27 implementation now keeps direct XML containment as the default and adds a **provisional structural-range rule** for sections: a `<section>` with no direct `<diag>` whose declared range strictly contains another sibling section becomes that sibling's parent. `sectionIndex` provides the authoritative `first`/`last` range when it covers the section; the section id supplies a documented fallback for the eight sections absent from `sectionIndex`. The current real build produces 63 `Section → Section` links under 12 grouping sections, including `C00-C96` → `C00-C75` → `C00-C14`…`C73-C75`; `T07-T88` → `T20-T32` → `T20-T25`/`T26-T28`/`T30-T32`; `V00-X58` → `V00-V99` → the 12 transport ranges and `W00-X58` → its 10 detailed accident ranges; and `Y62-Y84` → `Y62-Y69`/`Y70-Y82`/`Y83-Y84`. This uses official range metadata rather than a title heuristic, but remains in this file for discussion because the XML provides a flat `sectionIndex`, not explicit parent-child edges.

## Define the FY27 update treatment for legacy UMLS enrichment

The FY25 staging export stores `CUI` and `Semantic Types` on 97,903 concepts, but neither is supplied by the CMS/NCHS FY27 package. The local WHOATC legacy loader confirms that its equivalent fields came from UMLS/BioPortal, while no local ICD-10-CM loader has yet been found that documents the source, release, matching method, or intended maintenance policy for the ICD-10-CM values. The update cannot silently replace the `extras` object with only FY27 fields, because OCL replaces supplied extras wholesale. The project needs Joe's confirmation on whether these UMLS fields are intentional published enrichment to preserve or regenerate, or a legacy artifact to remove through a separately audited change.

## Resolve non-official UMLS semantic-type concepts before retirement

The FY25 ICD-10-CM export contains 127 active concepts with identifiers `T001` through `T204` (with gaps), such as `Organism`, `Plant`, `Fungus`, `Virus`, and `Bacterium`. They are UMLS Semantic Type identifiers, are absent from the official CDC/NCHS FY27 files, and form their own unrelated hierarchy in the Source. The same pattern was found in WHOATC. The apparent update action is to retire them using exact-uppercase `__action: "DELETE"`, but that action must wait for confirmation of why they were loaded and whether they are intentional published content. The same question applies to 38 synthetic range artifacts such as `B10-B10`: they are absent from FY27 because the official XML uses the bare structural code `B10`, but their retirement changes the existing hierarchy and must be reviewed with the full update diff.

## Confirm the release-version identifier and artifact names

`FY27` is the selected Source Version mnemonic and is recorded in `source.json`; confirmation is still required before a released OCL Source Version is created. Source, organization, and concept mnemonics remain space-free (`US-NCHS`, `ICD-10-CM`, `V00-V99`, `S52.521A`). The existing released staging version demonstrates that OCL permits a version identifier containing spaces, but that is not required for FY27 and is incompatible with the current export-download tool's mnemonic validation. The production-targeted artifact remains `bulkimport_icd10cm.bundle.zip`; staging and local rehearsal artifacts must carry `.staging` and `.local` respectively, and each audit must record the exact target environment, source snapshot, and create/update mode.

## WHO-ATC upstream authority decision (for meeting)

**Status: proposed; decision required at the meeting.** Recommend the WHO Collaborating Centre's official ATC/DDD Index as the authority for canonical ATC codes, preferred names, hierarchy, and lifecycle. Distinguish the BioPortal platform from the provenance of the resource it hosts: BioPortal describes this ATC ontology as an RDF version of the UMLS ATC ontology. We will not create CUI mappings or carry CUI/Semantic Type fields into the target Source. Selected BioPortal `skos:altLabel` values may be considered as optional aliases, but they remain UMLS-derived content and require explicit review, provenance, licensing, and an approved search use case.

The date comparison must distinguish classification edition from upload time:

- WHOCC labels its searchable classification [**ATC/DDD Index 2026**](https://atcddd.fhi.no/atc_ddd_index/), valid from **January 1, 2026**, and reports **Last updated: January 20, 2026**. The [separate updates page](https://atcddd.fhi.no/atc_ddd_index/updates_included_in_the_atc_ddd_index/) was last updated **January 22, 2026**.
- BioPortal's [ATC ontology page](https://bioportal.bioontology.org/ontologies/ATC) shows the latest submission uploaded **March 22, 2026**, but its underlying ATC source version is **2025_02_10**, released **November 3, 2025**. The Notes identify it as derived from UMLS 2025AA; the Source metadata lists UMLS 2025AB and 2025AA. A later BioPortal upload date is not evidence of a later ATC classification edition. The pinned local Turtle identifies UMLS 2025AB; use it only as a comparison snapshot and preserve its hash/provenance, not as the new source of truth.
- WHO published [decisions from its April 2026 meeting](https://atcddd.fhi.no/news/temporary_atc_ddds_including_alterations_from_the_april_2026) on **July 17, 2026**; the objection deadline was **August 20, 2026**. The WHOCC says decisions with no objection will be final and included in the January 2027 Index. Do not silently fold them into an Index 2026 build; define a separate policy for any 2027 preview.

### UMLS removal scope

If the meeting approves omitting CUI and Semantic Type enrichment from the WHO-ATC target Source, remove these fields from the new build and Source metadata:

- The `CUI` concept extra **and** the duplicate UMLS CUI `Note` description. The current build emits both; these are not OCL `Mapping` resources.
- The `Semantic Types` concept extra and its Source property definition.
- UMLS parser/model fields (`cui`, `semantic_types`) and the corresponding output properties/descriptions. Retain submission/hash/version provenance for any BioPortal-sourced aliases that are approved; do not present those labels as independent WHO content.
- The 127 existing active UMLS Semantic Type concepts (`T001`–`T204`, with gaps) are not ATC concepts; review/retire them via a separate audited update if absent from the target WHO-only Source. Do not fold these into a bulk action without confirming the live target and reviewing the audit.

Do **not** label every BioPortal-delivered field as UMLS: ATC codes, preferred classification names, hierarchy, `ATC Level`, and `Is_Drug_Class` describe the classification and need an explicit WHO-source replacement/model, not automatic deletion. `ATC Level` and `Is_Drug_Class` can be derived from WHO's five-level structure if the OCL Source still needs those properties. The pinned BioPortal file has `skos:altLabel` on 656 of 6,897 ATC classes, but the current builder does not emit them; treat them only as optional alias candidates, cross-check against WHO and review generic entries (e.g. “combinations”/“various”) before deciding whether any improve search. If there is no approved alias use case, import no BioPortal-only fields. The live Source's historical `REPLACED BY` mappings are from the legacy alterations workflow, not CUI mappings; decide their future separately. The current active build creates no `Mapping` resources.

If approved, define the cut-off policy for 2027 decisions and plan a separately audited migration; this recommendation does not authorize an OCL update.
